# Firestore data model

Ticknest stores each workspace's business data under its workspace document. Firestore Rules and callable functions use the workspace ID as the authorization boundary.

## Trusted writes

The browser must not write workspace owner identity, membership role or membership documents, or invitation documents. Callable Cloud Functions derive the user ID and email from the verified Firebase Auth token. `createWorkspace`, `createWorkspaceInvitation`, `revokeWorkspaceInvitation`, `removeWorkspaceMember`, `setWorkspaceMemberRole`, and `acceptWorkspaceInvitation` validate authority and write membership/invitation state through trusted code. `saveManualTimeEntry` creates and edits completed time entries: it checks membership and ownership, resolves catalog display names from the referenced client, project, and task, and rejects overlaps with the user's other entries or running timer in the same transaction as the write. `saveBudget`, `setBudgetArchived`, and `deleteBudget` let active owners and managers manage every budget, including their own and the owner's. `saveBudget` validates the calendar dates, range length, weekday minutes, and exception dates; requires an active member and an active project or client when a budget is created or its user or target changes; and takes the display snapshots from the member and catalog documents. Unchanged users and targets keep their snapshots, so a budget of a removed member or archived target can still be edited. `deleteBudget` refuses budgets that are not archived. Time off is written only by callables: `saveLeaveType` (owner only) creates custom types and saves any type's settings, including the built-ins; `setLeaveAllowance` and `addLeaveAdjustment` let owners and managers change any active member's allowance, except that a manager cannot change their own; `submitLeaveRequest` lets an active member request leave for themselves, counts the working days, rejects ranges that cross a year, have no working day, use half days on a full-day type, or overlap the member's own pending or approved requests, marks requests over the remaining balance, and approves on submit when the type needs no approval or nobody else may approve; `decideLeaveRequest` lets an active owner or manager approve or reject someone else's pending request, recomputing over-allowance on approval; `cancelLeaveRequest` lets the requester cancel a pending request or approved leave that has not started (in the requester's time zone snapshot), and an eligible approver cancel approved leave at any time. Firebase Admin credentials remain in the managed function runtime. Invitation tokens are single-use, high-entropy values; only their SHA-256 hashes are stored, and invitations expire after seven days.

Cloud Functions deployment currently requires Firebase's Blaze plan and a linked billing account. The plan has a no-cost usage quota, but exceeding its included usage can incur charges. See Firebase's [pricing-plan documentation](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans).

## Security rules

- Workspace documents can be read only by members. Owners can update only the workspace name (1–80 characters), week start (Sunday `0` or Monday `1`), and update timestamp; ownership cannot be changed by a client.
- Members can read workspace clients, projects, and tasks. Members can read only their own time entries; owners and managers can read every workspace time entry. Firestore queries by members must constrain `userId` to their authenticated UID.
- Owners can create, update, and delete clients, projects, and tasks.
- Members can read only their own budgets; owners and managers can read every workspace budget. Member queries must constrain `userId` to their authenticated UID. Budget writes are denied to all web clients and go through the budget callables.
- Members can read leave types. Members can read only their own leave requests and allowances; owners and managers can read every member's. Member queries must constrain `uid` to their authenticated UID. Every time-off write is denied to web clients and goes through the leave callables, so no client can set a status, approve its own request, or edit a balance directly.
- Members can start and stop their own timers directly. Completed entries are created and edited only through the `saveManualTimeEntry` callable, so overlap validation cannot be bypassed or raced; members and managers can edit only their own entries there and owners can edit any member's entries. Members and managers can delete their own completed entries and owners can delete any completed entry. Entry ownership cannot be changed by a client.
- Membership and invitation writes are denied to all web clients. Callable functions use the Admin SDK, which bypasses Firestore Rules, so those functions validate every input and check the authenticated user themselves.
- Unmatched collections and documents are denied by default.

## Indexes

The user workspace selector uses a collection-group query on `members` constrained by `uid == currentUser.uid`; the single-field collection-group index is managed by Firestore. Budget queries filter by `userId` and keep budgets whose `endDay` is on or after a given day, using the `userId` + `endDay` composite index. Time-off queries use only equality filters (`uid`, `status`, or `year in [...]`), which Firestore serves from single-field indexes. Add composite indexes alongside future queries when those features are implemented.
