# Firestore data model

Ticknest stores each workspace's business data under its workspace document. Firestore Rules and callable functions use the workspace ID as the authorization boundary.

All audit timestamps are written with server timestamps. Workspace and association names are bounded strings. Unknown fields are rejected by rules. Entries retain display snapshots so archival of a client, project, or task does not erase historical context.

## Trusted writes

The browser must not write workspace owner identity, membership role or membership documents, or invitation documents. Callable Cloud Functions derive the user ID and email from the verified Firebase Auth token. `createWorkspace`, `createWorkspaceInvitation`, `revokeWorkspaceInvitation`, `removeWorkspaceMember`, `setWorkspaceMemberRole`, and `acceptWorkspaceInvitation` validate authority and write membership/invitation state through trusted code. `saveManualTimeEntry` creates and edits completed time entries: it checks membership and ownership, resolves catalog display names from the referenced client, project, and task, and rejects overlaps with the user's other entries or running timer in the same transaction as the write. `saveBudget`, `setBudgetArchived`, and `deleteBudget` let active owners and managers manage every budget, including their own and the owner's. `saveBudget` validates the calendar dates, range length, weekday minutes, and exception dates; requires an active member and an active project or client when a budget is created or its user or target changes; and takes the display snapshots from the member and catalog documents. Unchanged users and targets keep their snapshots, so a budget of a removed member or archived target can still be edited. `deleteBudget` refuses budgets that are not archived. Firebase Admin credentials remain in the managed function runtime. Invitation tokens are single-use, high-entropy values; only their SHA-256 hashes are stored, and invitations expire after seven days.

Cloud Functions deployment currently requires Firebase's Blaze plan and a linked billing account. The plan has a no-cost usage quota, but exceeding its included usage can incur charges. See Firebase's [pricing-plan documentation](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans).

## Security rules

- Workspace documents can be read only by members. Owners can update only the workspace name, week start, and update timestamp; ownership cannot be changed by a client.
- Members can read workspace clients, projects, and tasks. Members can read only their own time entries; owners and managers can read every workspace time entry. Firestore queries by members must constrain `userId` to their authenticated UID.
- Owners can create, update, and delete clients, projects, and tasks.
- Members can read only their own budgets; owners and managers can read every workspace budget. Member queries must constrain `userId` to their authenticated UID. Budget writes are denied to all web clients and go through the budget callables.
- Members can start and stop their own timers directly. Completed entries are created and edited only through the `saveManualTimeEntry` callable, so overlap validation cannot be bypassed or raced; members and managers can edit only their own entries there and owners can edit any member's entries. Members and managers can delete their own completed entries and owners can delete any completed entry. Entry ownership cannot be changed by a client.
- Membership and invitation writes are denied to all web clients. Callable functions use the Admin SDK, which bypasses Firestore Rules, so those functions validate every input and check the authenticated user themselves.
- Unmatched collections and documents are denied by default.

## Indexes

The user workspace selector uses a collection-group query on `members` constrained by `uid == currentUser.uid`; the single-field collection-group index is managed by Firestore. Budget queries filter by `userId` and keep budgets whose `endDay` is on or after a given day, using the `userId` + `endDay` composite index. Add composite indexes alongside future queries when those features are implemented.
