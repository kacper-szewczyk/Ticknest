# Firestore Rules emulator test matrix

Every row below, the boundary-validation cases, and the callable flows are automated. `npm run test:emulators` runs them against the Auth, Firestore, and Functions emulators:

- [`tests/emulator/firestore-rules.test.ts`](../tests/emulator/firestore-rules.test.ts) has one `matrix(...)` block per row, run as an unauthenticated client, an authenticated user with no membership, a workspace member, and the workspace owner.
- [`tests/emulator/functions.test.ts`](../tests/emulator/functions.test.ts) calls the workspace, invitation, and membership callables with Auth emulator users.
- [`functions/test/manual-time-entries.test.mjs`](../functions/test/manual-time-entries.test.mjs) covers `saveManualTimeEntry`.

Fixtures are written with rules disabled, the way trusted Admin SDK code would write them. When a rule changes, update this table and its test together.

For time-entry reads, verify that a member can directly get and query their own entries but cannot directly get another member's entry or run an unconstrained query over the collection. An owner can directly get and query entries for every member. Also verify boundary validation: unknown fields, oversized names/descriptions, invalid enum values, malformed timestamps, negative estimates, and completed entries with an end at or before the start must be denied. Direct client creates of completed entries and direct edits of completed entries must be denied; only starting and stopping a running timer, and changing a running timer's client, project, task, and billable state to active catalog items, is allowed from the browser. Verify the callable flows separately in the Functions emulator: `saveManualTimeEntry` rejects overlapping entries (including concurrent conflicting saves, of which only one may succeed) and entries that overlap a running timer, lets an edit overlap its own previous time, and lets only owners edit another member's entry (covered by `functions/test/manual-time-entries.test.mjs`); only an active workspace owner can create or revoke invitations and remove members; invitation acceptance requires a matching verified email, pending status, and unexpired invitation; repeated acceptance is denied; the owner cannot remove themselves or another owner. After removal, the former member must lose workspace reads and writes, while the owner can still read the retained membership identity and historical time entries.
